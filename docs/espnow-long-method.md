# ESP-NOW連続指令とWi-Fi共存の評価方法

ROS 2と省電力設定の完了後、既存のESP32 2台へ長時間記録用ファームウェアv2を書き込み、実機pilotと実TCP通信を確認した。使用者の終了希望を受け、各600秒の19試行で測定を終了した。8条件を2〜3反復し、全記録と停止宣言を独立検算した。残り5試行は未実施であり、予定24試行を完了した結果として扱わない。元のフラッシュは非公開バックアップを保持する。

## 構成と試行

ESP-NOWは同じ机上のESP32 2台で64 byteのアプリ要求をユニキャストし、相手が応答する。Ch6・20 MHz・1 Mbps長プリアンブル・暗号化なし・省電力OFF。予定周期20・50・100・200 Hz、別系統Wi-Fi待機／TCP負荷、3反復の計24試行を各600秒連続で実施する。実施できた時間は保存結果で確認し、予定時間だけから連続測定できたと扱わない。先に短いpilotを行い、pilotは正式集計に含めない。

別系統Wi-Fiは観測PCのCh6・20 MHz APにラップトップ2と3台目のESP32が接続する。ラップトップ2からESP32へTCP payloadを要求15.72864 Mbpsで生成する。実受信量と送信側の未送信bytesを保存する。待機条件にもAPビーコン・接続維持・監視通信があり、無線信号が完全にない条件ではない。他チームの重い通信の再現には実受信の維持を確認する必要があり、TCPを要求しただけで全時間に一定のRF負荷を印加したと判断しない。

配置は使用者の報告に基づく同じ机上・各機器おおむね30 cm、固定とする。正確な距離・アンテナ方向は未測定。WROOM-32／32D系の2台の製品名とUSBポート対応は未確認で、M5 ATOM LITEを含む2台で行う。SDRはESP32-C5-WROOM-1。配置変更は別の試験系列として記録する。

## 連続アプリ記録と整合性

送信予定時刻・API呼出し・応答callback・未生成slotを、送信機の単一monotonic時計で記録する。遅れたslotはまとめて飛ばし、過去の指令を追いつくまで大量送信しない。600秒終了後に2秒の応答猶予を設ける。送信APIの成功と無線MAC送信完了とアプリ応答は異なる。MAC成功・失敗は集計値で保存し、個々のsequenceの成功へ割り当てない。

Wi-Fi callbackではUART出力をせず、512イベントの待ち行列へ非ブロッキングで記録する。別タスクが最大128イベントのCRC32付きバイナリブロックを115200 baudで送る。イベントは種別・sequence・相対時刻・引数の各uint32、計16 byte。応答側の送信待ち行列は64パケットで、以前の短時間試験と同一実装とは扱わない。UARTのCRC、全ブロック数、終了マーカー、予定slotの全被覆、イベント数と実機カウンターの一致、記録待ち行列のdrop=0を確認する。記録不備をRFによる指令欠落として数えない。

200 Hzでも連続した全アプリイベントを保持し、最大途絶を間欠的なSTATUS表示から推定しない。別のスレッドでWi-Fi受信量と送信側カウンターを約10秒ごとに取得する。HTTPの待ち時間が送信機UARTを詰まらせないよう、UART受信・RF取得・監視を分ける。監視の失敗は欠損として保存し、接続や受信量が維持されたと補完しない。

応答機の別UARTから同じ周期で受信数・RSSIも保存する。RSSIは最後に届いたパケットの値で、10秒間の平均や全パケットの分布ではない。前回から受信数が増えない区間では、新たなRSSIが観測できたと扱わない。送信機のUARTへ測定中のSTATUS要求を送らず、バイナリ記録との混在を避ける。

## 評価指標

全予定指令のうち予定時刻から20 ms以内の応答がない割合を算出する。未送信、API失敗、応答欠落も含む。別に、実際にAPIを呼び出した指令の呼出し時刻から20 msの期限超過を示す。RTT p99は応答が戻った指令に限るため、欠落が多いときに小さいp99だけで優れた通信と結論しない。

10秒窓の期限超過・RTT p99、連続応答欠落、連続期限超過、最長応答途絶、sequenceが更新されない最長時間を記録する。最後の指標では順序が戻った古い応答が来ても更新扱いにしない。最長途絶には試行の開始・終了端点を含める。連続欠落数は周期に依存するため、20 Hzと200 Hzの比較では時間の指標も併記する。アプリの応答途絶はロボットのモータ停止や安全動作を試した結果ではない。

## SDRと成果物

C5は80 MS/s、16380 I/Q、アナログ帯域48 MHz、LO2442 MHz、手動ゲイン20。DC除去・Hann窓・FFT1024、CRC検証を行う。青と緑の図は共通の−90〜−45 dBFS、縦軸は間欠取得順とする。UARTの連続アプリ記録と異なり、SDRの各snapshotは204.75 µsで、取得の間のRFは観測していない。RF観測時間比を表示し、色から占有率・通信成功率を求めない。Wi-FiとESP-NOWのパケットを画像だけで識別したとは主張しない。

公開データではMAC・ホスト名と私有時計の起点を除き、各時計の相対値を保存する。`make operational-espnow-long`で保存済み全試行・CRC・イベント被覆・カウンター・数値・公開ファイルのSHA256・宣言された終了範囲を検算してから、統合指標、経時変化、青緑SDR図を生成する。正式な図は実測データから作成し、描画確認用の合成データを結果へ混ぜない。

## 保存中断と取得セグメント

当初の有効7試行を保存した後、次の600秒試行はアプリ記録とI/Q取得を終了したが、測定後のI/Q圧縮が旧15秒の保存待ちを超え、最終contextを保存できなかった。12000送信・12000応答の全アプリ記録を補足として保持し、元I/Qは非公開保管する。この試行の未確認の終了設定やWi-Fi負荷量を補完せず、正式24試行へ含めない。

RF・アプリ測定窓を変えず、測定後のI/Q保存待ちを120秒へ延長した。アプリ記録の保存時点で私有checkpointを作り、失敗時も事前設定と取得済みのイベントを保持する。実機pilotで保存と終了を確認してから、有効な7試行を保持し、未完了17試行のみを取得する。再開試行には取得セグメントを記録し、中断前後の環境が等しかったと仮定しない。

配置比較は後続の別系列で各10秒・100 Hzとする。そこでは監視カウンタを2秒ごとに取得し、長時間系列の10秒ごとの監視と区別する。短時間比較の結果を10分試行へ追加して同じ耐久性の母集団として集計しない。
