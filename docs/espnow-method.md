# ESP-NOWと独立したWi-Fi負荷

追加ESP32-1→ESP32-2へ64 byte・100 Hzの未暗号化unicastを送り、受信タスクが同じ内容をアプリ応答として返します。APを通りません。受信コールバックは短く保ち、echoはキューから別タスクで送ります。送信側の同じµs時計で往復遅延を記録し、MAC送信成功・失敗とアプリ応答の成功を区別します。アプリ再送は実装していません。送信APIが受付しなかった要求も送信要求数の分母に含め、応答欠落とAPI受付失敗を物理層の損失率へ読み替えません。

PHYは1 Mbps・long preambleへ明示設定し、受信metadataのrateとsig_modeを読み出します。Wi-Fi側は観測PC（Intel BE200）のCh6・20 MHz APを固定し、ラップトップ2（MT7921E）→AP→ESP32-3へ大容量TCP模擬データを流します。要求15.73 Mbpsと実受信量を分けます。ESP-NOW側のCh6・Ch7・Ch11とWi-Fi待機・負荷の6条件、各30秒・3反復です。順序は反復内で無作為化します。

ESP-NOWのRTTは指令からアプリ応答までで、ACKだけの時間ではありません。20 ms期限超過には欠落を含み、p99は戻った応答の分位点です。終了後1秒を欠落判定の猶予とします。UARTは115200 baudで、時刻列をCRC32付きバイナリとして測定後に読みます。UARTダンプ時間はRTTに含めません。Wi-Fi受信量のカウンタ差には読み出し時間が含まれるため、その実際の区間長でMbpsを求めます。

位置はESP32-1/2間75 cmを維持します。先行のUDP経由AP中継と比べると送受信機・無線経路・PHYが違うため、RTT差をESP-NOWという方式だけの効果としません。画像・点群をESP-NOWで大容量転送する試験、同一チップ上でWi-FiとESP-NOWを併用する試験、暗号化、移動、距離掃引は含みません。特にWi-Fiに接続した同じ無線を使う運用では、接続APとチャネルの関係があるため、本試験の独立無線構成と区別します。

C5は既存と同じ80 MS/s・16,380 I/Q・48 MHzアナログ帯域・手動ゲイン20・FFT1024、LO2442 MHzです。共通の−90〜−45 dBFS尺度で実測画像を示します。未校正・間欠取得・周波数位置による感度差は同じ制約です。元I/Q・MAC・元フラッシュは非公開保管、公開するのは相対時刻・FFT・匿名条件です。

Espressif公式 [ESP-NOW Programming Guide](https://docs.espressif.com/projects/esp-idf/en/v6.0/esp32/api-reference/network/esp_now.html)も参照してください。

Wi-Fi負荷helperにはTCP keepaliveと閉鎖検出を加え、ボード再起動時の半開接続を処理します。待機もAPビーコンやTCP接続維持を含み、無線停止ではありません。先行69試行はこの変更前の`b5af98b`に保存したhelperを使用しました。
