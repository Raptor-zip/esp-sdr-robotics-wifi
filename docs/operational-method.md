# 流量制限と送信周期の評価

観測PC（Intel BE200）はCh6・20 MHzのAP、ESP32-3はコントローラー役、ラップトップ2はロボット役である。指令64 byte・100 HzのUDP往復と逆方向のTCP模擬データはSTA→AP→STAを通る。他チームはESP32-2 APからESP32-1 STAへの飽和TCPで、Ch6・7・11を変更する。ラップトップ1（Intel AX210）の有線インターネット供給は維持する。

今回の配置は、全PC・マイコンが同じ机上にあり、各機器間はおおむね30 cmで固定している。使用者が測定開始後も配置は変更しておらず、人の影響をほとんど受けない位置関係と確認した。各組合せの正確な距離や向きは未実測である。先行実験で報告されたESP32間75 cm・C5から40/90 cmという値を今回の距離として使用しない。配置比較の段階でのみ条件を変更し、実測位置を記録する。

使用者が報告したボードはESP32-WROOM-32、M5 ATOM LITE、ESP32-WROOM-32D、ESP32-C5-WROOM-1である。負荷用APのESP32-2はM5 ATOM LITE（実機のチップ識別はESP32-PICO-D4）、SDRはESP32-C5-WROOM-1として記録する。ESP32-1と指令役ESP32-3はWROOM-32／32D系だが、製品名と各USBポートの対応は未確認である。製品名だけから個々の実機のアンテナ状態や低RSSIの原因を断定しない。

流量制限は要求0・0.25・0.5・1・2 Mbps、TCP byte生成周期100 ms、他チーム3チャネル、3反復、各30秒・3,000送信の45試行とする。周期比較は要求0.5・1 Mbps、生成周期10・100 ms、他チーム3チャネル、各3反復の36試行とし、流量制限と区別した反復内の無作為な順序で取得する。確認用pilotは集計に含めない。

負荷の生成byte数は、生成tick数×要求Mbps×周期/8で決める。TCP逆圧で送れなかった生成量はアプリの未送信量として残り、同じ試行中に持ち越す。`generated_payload_bytes`、送信側ソケットが受け付けた`sent_payload_bytes`、差の`pending_application_bytes`と、受信側の実受信量を分ける。TCP byte streamであり、実カメラのフレーム・コーデック・点群内容を再現したものではない。10 ms生成に変更してもRF送信が均等になったとは仮定しない。

主取得のTCP源はhelper version2を使用する。設定を切り替える際にsender側で旧TCPをRSTで終了し、前条件のソケット受付済みデータを次の計測窓へ残さないようにする。再接続後の `tcp_connection_generation` と `configuration_generation` の一致を確認し、3秒ウォームアップ後に計測する。これによって要求と実受信が必ず同じになるとは仮定せず、両方を記録する。

TCP実受信はESP32-3のベンチマーク30秒窓で数える。他チームのカウンタ区間は、応答終了猶予とUART読出しも含むため、その区間の実時間で換算する。要求量を達成したとは仮定しない。自チーム・他チームとも実受信を残し、等しい要求量を等しい空中時間へ読み替えない。

他チームのTCP接続成立を確認してから負荷を開始する。3秒の負荷ウォームアップ後と計測後に接続状態を記録する。負荷中にTCPが切れて再接続する場合も観測結果として残し、不利な試行だけを除外しない。飽和負荷の設定が継続的なRF送信を保証するわけではなく、実受信量と接続状態を併記する。

version6の予備取得では、Ch11・要求0.5/2 Mbps・反復3の2試行で、他チームのAPソケットが計測中にそれぞれ98304 byteを受け付けた一方、STA側の実受信増加は0だった。これを受信不達の結果として保持し、両チームの受信が続いた条件と区別する。旧版でAP・STA双方のカウンタが停止した試行とは異なる。`other_socket_accepted_mbps` はAPソケットの受付量であり、RF送信量・空中時間・受信成功量とは扱わない。このversion6の診断記録は私有保管し、正式集計には混ぜない。正式集計は新たに取得したversion7の全試行を使用する。検算は送信・受信カウンタと不達の分類を確認し、双方のカウンタが停止したデータ経路を負荷成功として通さない。

他チーム用の初期14試行では、実受信0の試行が2件あり、接続処理の対策前に取得を止めた。その元データと確認用pilot・途中のI/Qは非公開の別ディレクトリに保管した。version6でも45試行の流量比較と15試行の周期比較を取得したが、周期比較で接続表示があっても両データカウンタが停止する試行を確認した。これらは非公開の予備診断記録として保管し、正式な比較結果には使用しない。

主解析には `operational-wifi`（STATUS version 7）で新たに取得した45試行・36試行を用い、旧版の反復を混ぜない。接続時にSTAのnonce、APの新たなchallenge、STAの応答を交換して現在の相手を確認する。負荷開始前に両端の `tcp_peer_ready`、同じnonce/challenge、実チャネル・省電力OFFを確認する。LOAD応答、実設定1000（未ペーシング）、負荷の残り時間、送信試行数、EAGAIN、ソケット受付量、受信量を別々に残す。idle時に相手のEOFも検知する。新しい応答確認が無線不達をなくすとは仮定せず、負荷中の悪い結果を保持する。CPU240 MHz、FreeRTOS1000 Hz、TCP送受信バッファ32768 byteの設定は従来版と同じ。測定バイナリ・設定とソースのSHA-256を `experiments/firmware/operational-wifi/binaries/sha256.json` に保存する。

version6の予備取得でも26試行の後、次のCh11試行の接続準備が失敗して処理が終了した。測定・負荷開始前の失敗であり、完了した26試行は悪い結果も含めて保持した。負荷用の2台を同じバイナリのままハードリセットし、Ch11接続と実受信の回復を確認して未取得分を再開した。机上配置は変更していない。取得前の接続状態は再開後から最大2回まで記録して再試行するが、測定開始後の性能結果を良いものへ取り替えない。中断・再起動と、その前後の試行を解析に残す。受信量・RSSI・遅延の変動には端末状態と環境の影響も含み、チャネルだけが原因と断定しない。

指令のRTTは送信側の同じµs時計で取得する。予定送信と実送信の差も残す。p99は戻った応答に対する分位点、20 ms期限超過は欠落を含む。3,000送信後1秒を応答猶予とする。各条件3反復とパケット数を区別し、パケットを独立した環境反復と扱わない。

C5は80 MS/s・16,380 I/Q・48 MHz・手動ゲイン20・FFT1024・LO2442 MHz。CRCを全取得で確認する。公開FFTの色尺度は−90〜−45 dBFSで共通、DC除去とHann窓を使用する。間欠取得順は連続時間ではなく、未校正dBFSから占有率や絶対電力を求めない。指令との時計対応はUART開始時刻による近似で、パケット単位の一致ではない。

公開データは`experiments/data/operational/limit/`と`shape/`へ役割別に保存する。元I/Q・元フラッシュ・元ホスト情報は非公開保管する。元の69試行は`b5af98b`、ESP-NOW18試行のhelperは`44f0ec4`までの履歴で区別できる。本測定は別helper `operational_traffic.py`を使用する。

取得終了後、流量制限は `make operational-limit`、周期比較は `make operational-shape` で解析・全条件の検算・図生成を順に実行する。`--require-complete` は、それぞれ45・36試行の全条件と各3反復が揃わない限り失敗する。途中解析が通常の数値検算を通っても、取得完了とは区別する。
